VERDICT: HAS FINDINGS

## Blocking findings

- **B1: Repo↔project-UUID binding is deferred to a possible waiver, contradicting binding ADR-802 §16**
  Evidence: CDP-1-spec.md:1013-1018 (question 3: "Publishing into the wrong project remains possible until that binding exists… must be resolved or explicitly waived for the first write") and CDP-1-spec.md:1083-1085 (gate 9: "must be resolved or explicitly waived"). ADR-802.md:323-331 (§16): the broker may be used only by the §14 paths "only when all of the following are implemented and enforced in code: … backend identity binding (project UUID ↔ repository identity)". live-smoke.md:99 and :81 confirm the residual is real ("repo↔project-UUID binding missing", listed as an open §16 condition).
  Why it blocks: CDP-1 is a §14 C-now path, so ADR §16 binds it. A waiver is not "implemented and enforced in code"; the spec cannot authorize L1 under the current ADR without either landing the binding or formally superseding/amending ADR §16. M2/M3 (CDP-1-spec.md:388-390) validate the manifest against the *configured* UUID only — a misrouted or wrong-project publish passes every check.

- **B2: §5.7 reconciliation classifies "same op_id, equal semantic identity, different payload_sha256" as terminal Diverged, directly contradicting §2.4**
  Evidence: CDP-1-spec.md:536-540 (reconcile: LANDED requires `manifest.payload_sha256 == payload_sha256`; "otherwise => DIVERGED (op id reused / overwritten)") vs CDP-1-spec.md:216-221 (§2.4: "Same S, different compressor implementation ⇒ different bytes, same semantic identity… a differing payload with equal `W` and equal `state_sha256` is `AlreadyCurrent`, not divergence"). See also CDP-1-spec.md:193-196 ("compression_impl is provenance, not a reader requirement"; a different compressor build "must allocate a new op_id; they must not assume a byte-identical replay").
  Why it blocks: the reconcile pseudocode is labeled normative (Appendix A, CDP-1-spec.md:1175-1195, same rule at :1183-1187). The Diverged branch keys on `payload_sha256` (compressed bytes) while §2.4 defines divergence on semantic identity. The scenario is reachable: a publish crashes after landing, the attempt record survives (Appendix C keeps `payload_sha256`), the dependency is bumped before recovery, and the recomputed/re-recorded payload differs — the operator gets a terminal, manual-intervention Diverged for a benign replay. The two normative rules must agree (compare `source.commit` + `state_sha256` in reconcile; treat payload-digest mismatch alone as LANDED/no-op).

## Non-blocking findings

- **N1: Deterministic refusals are collapsed into `ReconcileRequired`, conflating "refused, safe to re-plan" with "unknown, writes blocked".** Evidence: CDP-1-spec.md:1147-1148 (Appendix A: `Refuse(reason) -> … return ReconcileRequired(reason)`) vs §5.6 (CDP-1-spec.md:518: ReconcileRequired = "unknown or unprovable; writes blocked") and §5.7:563-565 (blocked state gates every subsequent publish). `CandidateStale`/`WrongProject` are provable and not blocking; §5.6's taxonomy has no `Refuse` outcome even though §5.3 defines one and T10 (CDP-1-spec.md:942) asserts "refuse if candidate stale". Fail-safe direction, but the attempt record could be spuriously set to blocked.
- **N2: `LandedSuperseded` depends on the deployed broker serving `verify` at non-head historical commits — confirmed in mock/stub only.** Evidence: mock.rs:8-10 and tests-state_broker_contract.rs:958-1000 (historical verify works); live-smoke.md:63 verified digests only "at pinned head"; live-smoke.md:118-119 ("the adapter's reconcile path… was not exercised live"). §5.7 (CDP-1-spec.md:541-544) requires `verify(X, owned_paths)` at a superseded commit X. If the deployment only serves head-pinned verify, LandedSuperseded degrades to NotLanded (benign but the taxonomy assumes the stronger primitive).
- **N3: The manifest is unauthenticated; a self-consistent forged manifest passes all reader checks for a broker-only consumer.** Evidence: CDP-1-spec.md:423-425 (no self-digest), §4.3 M1–M16 are all self-referential or config-compared; CDP-1-spec.md:1037-1041 (question 8) acknowledges this. ADR-802.md:84 and CDP-1-spec.md:627-630 bound the damage to advisory reads, but the resolution of question 8 (no hydration-privileged broker-only consumer) is a precondition, not a design property.
- **N4: Appendix B reader pseudocode omits the pinned-commit and inventory↔blob cross-checks that §6.2 mandates.** Evidence: CDP-1-spec.md:1204-1234 (no `m_raw.commit != C`, no inventory comparison, no `Err(ProtocolMismatch)`/`InventoryMismatch`) vs CDP-1-spec.md:641-655 and :687-689. Both are labeled normative; an implementer following Appendix B would ship the exact TOCTOU gap T39 is supposed to catch.
- **N5: Leftover inconsistency `0000..0031`.** Evidence: CDP-1-spec.md:743 ("Slots are fixed at `0000..0031` (practically `0000..0003`)") vs MAX_SLOTS=4 (CDP-1-spec.md:236) and the owned set `0000..0003` (CDP-1-spec.md:453-454); live-smoke.md:109 still says "≤32 chunks". Editorial, but the ownership set and slot ceiling must be stated once.
- **N6: The commit message template is unspecified.** Evidence: CDP-1-spec.md:1152 (`message: commit_message(S, W, chunks)`) with no definition; validate.rs:99-128 requires a single non-empty ≤512-char line, no C0/DEL, and no leading `Project-UUID:`/`Broker:`/`Broker-Op:`. A naive JSON-embedding of `W` (multi-line) would be rejected as `invalid_input` at the first real publish — zero broker calls, but the spec claims fail-closed preflight coverage of every input.
- **N7: Equal-watermark Diverged can be triggered by benign schema/serialization drift.** Evidence: CDP-1-spec.md:477 (`EqualWatermarkDifferentContent` hard block); checkpoint.rs:17-50 shows the serialized shape is version-dependent (serde field additions change bytes). Since S's bytes are git-addressed this is genuinely different content, so the hard block is correct, but two clients on different Crosslink versions publishing different S with equal W will mutually wedge until an operator intervenes. Document the operational expectation.

## Incorrect or unsupported assumptions

- **Decoded-bytes limit accounting (§8.5).** The derivation assumes the broker counts decoded content. Supported client-side (validate.rs:16-17, client.rs:383-394 and the stub at tests-state_broker_contract.rs:837-843 both check decoded lengths) but unsupported against the deployment: live-smoke.md:122 explicitly never tested size limits. The spec correctly marks this must-verify (CDP-1-spec.md:827-836, §12 item 12); no near-boundary publish until resolved.
- **Cross-version/platform gzip byte determinism.** §2.4's "same compressor ⇒ byte-identical" is asserted, not proven; question 2 (CDP-1-spec.md:1008-1012) concedes it. Mitigated: classification precedes any write, so replay-no-op holds via semantic identity regardless (§5.3:476-477); the residual exposure is exactly B2.
- **`verify` at historical commits on the deployed broker** (see N2) — unsupported by live evidence.
- **"Two independent publishers that publish the same S produce the same semantic identity"** (CDP-1-spec.md:127-131) — supported for `state_sha256`/`S` by construction, but only if both read the *same pushed* S; the P1–P5 preflight (§1.1) enforces this per-invocation, and the evidence (hub_v3-excerpts.rs:21, sync-cache-excerpts.rs:44-85) confirms the ref layout and fetch proof are real.
- **Capacity arithmetic — verified correct:** 1,048,576 − 4,096 = 1,044,480; ceil(1,044,480/262,144) = 4; slot 3 max 258,048 ≤ 262,144; 5 files ≤ 32; payload 262,144→1 slot, 262,145→2; 1,044,480 OK, +1 fails (T21). No off-by-one found. The cap is conservative by exactly 4,096 bytes versus the physical 4×262,144 — safe, not a defect. The §8.5 alternative figure (782,336 payload under wire accounting) is internally coherent (1 MiB wire ≈ 786,432 decoded base64 payload).

## Missing invariants / missing tests

- No test for **B2**: same op_id at head, equal `source.commit`/`state_sha256`, differing `payload_sha256` → must be Landed/no-op per §2.4, not Diverged.
- No adversarial test for a **forged-but-self-consistent manifest** against a broker-only reader (T36 tests profile labeling, not forgery resistance) — pairs with N3.
- No **zip-bomb** test: §6.2 promises bounded decompression (CDP-1-spec.md:690-691) but T01–T39 contain no payload that decompresses beyond `MAX_STATE_BYTES`/`m.source.state_bytes`.
- **T18 is ambiguous**: it asserts NotLanded when "head moved past our commit and carries no op id", but §5.7 (CDP-1-spec.md:541-544) yields LandedSuperseded whenever the error carried commit X ≠ head and `verify(X)` matches. The test must pin whether the error carries a commit sha.
- No test for **concurrent bootstrap** (two publishers, both `expected_head = null`): one lands, the loser's stale_state → re-classify → AlreadyCurrent/Supersede.
- No watermark **ordering-across-agents** test (derived `Ord` on `(timestamp, agent_id, agent_seq)`; T30 covers formatting only) and no test that a candidate from a lagging agent's clock is refused, not silently superseded into.
- No boundary test at the **H level** for manifest 4096/4097 (T21 is U) and no op-id grammar boundary test.
- Missing invariant worth stating: `checkpoint/state.json` (projection) must never be re-publishable as a source — §1.4 forbids it, but no test asserts the publisher refuses the projection path as input.

## Readiness

ready after named corrections — The protocol's core is sound: copying the pushed blob keeps the broker strictly derived (Focus 1: the only inputs are P1–P5-proven git objects, CDP-1-spec.md:70-86; prune/lock/display-id are walled off at :59-61 and :109-111); the watermark classifier is fail-closed in every ambiguous direction; the digest ladder, pinned-commit reads, single-commit rule, and old-slot inertness argument (§7) are coherent; the capacity math checks out independently. B1 and B2 are narrow, precisely-located defects: B1 requires the repo↔UUID binding (or a formal ADR §16 amendment) before L1, and B2 is a two-line normative fix plus a regression test. N1–N6 should be folded into the implementation issue but none changes the architecture.
