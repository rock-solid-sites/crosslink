## 1. Architecture assessment (Q1, Q3)

**Verdict: as delivered, the change is safe and additive — the existing persistence model is untouched (default `Local`, no production call sites, read-only CLI: `config.rs:356-380`, `commands/state_broker.rs:21-31`). But `ProjectStateTransport` is not the boundary it claims to be. It is a faithful *port of broker v1's HTTP API* dressed as a backend-neutral persistence seam, and the §4 mapping question it defers is the actual architecture.**

Observations (distinguished from interpretation):

- The trait (transport.rs:96-124) has five methods whose *shapes are broker semantics*: `op_id`, `previous_head`/`head_after`, per-file read-back `VerifiedFile`s, whole-tree `expected_head`. There is no notion of per-ref heads, append, or delete — i.e., the trait has already decided "one tree, one head" before the §4 decision was made (design doc admits this at §4: the mapping is "intentionally not made here").
- The trait's *provided methods* embed broker-v1 wire details: `commit_cas` reconciles by parsing `Broker-Op:` trailer lines out of commit messages (transport.rs:186-232, 283-292). Any substitute backend must reproduce the broker's trailer convention to be usable with `commit_cas`. That is coupling inside the "narrow seam," not behind it.
- `hydrate_into` is a provided trait method that does local `std::fs::write` (transport.rs:140-186). It is a consumer-side composition of `read_state` + `read_blob` and does not belong on a transport abstraction; it also makes every backend implicitly promise "materialize full inventory."

Interpretation: the honest description of this seam is "typed client port for broker v1, plus a mock." That is a legitimate deliverable and well executed at that level. What is not yet legitimate is the module doc's claim of a general "persistence seam between Crosslink and a durable project-state backend" (transport.rs:1-4, mod.rs:9-12). If the §4 decision lands on anything other than "one whole tree," the trait's `commit`/`commit_cas`/`read_state` shapes are the wrong shape and would be reworked.

Does the adapter preserve the v3 model (Q3)? Today, yes — trivially, by not touching it. Latently, no: the broker v1 contract cannot express two v3 invariants:

- **REQ-11 prune** rewrites an agent's own ref non-fast-forward after the covering checkpoint is durable (hub_v3-excerpts.rs:1650-1690 "Prune safety invariant"). The broker is fast-forward-only with **no delete** (broker/README.md "Replay" section; SECURITY-NOTES.md limitation 4). Under broker authority, event logs can only grow until they hit the 256 KiB/file / 1 MiB/commit limits, at which point the model dead-ends.
- **Per-agent writer authority**: v3's concurrency model is "each agent writes exclusively to its own ref; the plain push IS the CAS" (hub_v3-excerpts.rs:27-31). The broker replaces this with global whole-tree serialization (see §4 below).

So: no second model is *active*, but the ingredients of a competing one (single durable tree under `.crosslink/state-projection/` conventions, broker-shaped CAS) are now in-tree, and the projection test (`tests.rs:247-322`) demonstrates a read pipeline whose write-side counterpart does not exist.

## 2. Unnecessary complexity (Q2)

The +5515/-1 decomposes roughly as (diff/stat.txt): production code ~2,650 lines (client 756, config 708, transport 389, error 405, validate 316, mod 74, digest 35, commands 160, minus embedded unit tests), test scaffolding ~2,050 (contract stub 1,241; mock 441; tests.rs 342; live 86), docs/handoffs ~500, Cargo/docs plumbing ~35.

Removable without sacrificing correctness:

1. **The mock (`mock.rs`, 441 lines) is a third implementation of broker CAS semantics.** The loopback stub already implements the same contract over real HTTP with stricter fidelity (it keeps commit history and re-validates bodies — contract.rs:57-64, 962-1041). The mock's unique value is in-process unit tests of `commit_cas`/`hydrate_into`, which the stub client could serve just as well. Keeping both means every future semantic change is made three times (broker TS, mock, stub). Pick one; the stub is the more faithful one. (The mock's `inject_competing_commit` is trivially expressible against the stub.)
2. **A third copy of broker validation lives in the stub** (`stub_path_ok`, `stub_message_ok`, `stub_op_id_ok`, `stub_validate_commit_body`, contract.rs:890-1002). The post-Hy3 rationale (independent re-validation) is sound, but it hardens a 900-line hand-rolled HTTP server into permanent test infrastructure. At minimum, factor the independent validators into a shared `#[cfg(test)]` module rather than test-file locals.
3. **Speculative API surface**: `BrokerErrorCode::ALL` (error.rs:50-64) has no user in the packet; `StateBackend::into_broker` (config.rs:396) is unused; `StateBrokerConfig::state_branch()` exists only to be called by `is_state_ref` and one test (config.rs:284, 533). Each is small, but each is contract surface that must be kept correct.
4. **`VerifiedFile` vs `VerifiedEntry`** are near-duplicate types (client.rs:203-257); `VerifiedFile` could be `VerifiedEntry` + `verified: bool`.
5. **`#[allow(unused_imports)]` re-export block** in mod.rs:53-73 exists only because the bin and lib each compile the module tree — a pre-existing pattern, but it means ~70 lines of re-exports that exist for a compilation artifact.
6. Hand-rolled HTTP parsing in the stub (read_request/percent_decode, contract.rs:157-260) is ~100 lines that a test-only dependency would eliminate; defensible either way.

What is *not* over-engineered, despite appearing so: the redaction machinery, the client-side limit mirror (validate.rs), and the typed error taxonomy all pull real weight — the contract is adversarial about secrets and limits, and the tests prove it (contract.rs:1034-1076).

## 3. Semantic risks

### Q5 — paths by which a disposable projection becomes authoritative

1. **No persisted freshness marker.** `ProjectionReport` carries `commit` in memory (transport.rs:36-52) but nothing is written beside the projection recording which head it came from. Compare the v2 path's `LAST_HYDRATED_REF_FILE` marker plus fail-closed decision (hydration-excerpts.rs:417-457). `read_checkpoint(&projection)` (tests.rs:309) cannot distinguish "projection of head H1" from "hub cache at H1"; `hydrate_from_state`'s only guard is *emptiness* (hydration-excerpts.rs:361-366), not staleness — a non-empty stale projection hydrates happily and silently regresses SQLite. The moment any future code points a hydration entry point at `default_projection_dir`, a stale projection becomes the input that overwrites shared state.
2. **Silent backend revert on corrupt hook-config.** `read_hook_config_backend` returns `None` with only a `tracing::warn` when `hook-config.json` is unparsable (config.rs:437-443), and `StateBackend::resolve` treats `None` as `Local` (config.rs:377-381). The design doc's "there is no silent fallback" (§3.3) is contradicted here: an operator who selected `broker` via config file, then suffers a corrupt config, silently has durable writes routed to the local git path — the *opposite* direction of the double-authority hazard, but the same class of failure (two stores, wrong one wins). An env-selected backend is immune; a config-selected one is not.
3. **Write-from-projection hazard (future).** Nothing prevents a future flow from reading a projection to build a `CommitRequest` instead of re-reading the head. The adapter currently has no write callers, so this is latent, but the "commit from local state" pattern is exactly what `CommitRequest::single` invites.

### Q6 — stale-state reconciliation and `commit_cas`

What it gets right: op-id-required (transport.rs:199-204), blind retry never happens, the Hy3 major finding is genuinely fixed — the `already_applied` branch now compares `sha256`/`size` against the *intended* payload (transport.rs:215-247), and the regression test (`tests.rs:132-166`) covers the reused-op-id-overwrite case. Trailer spoofing is correctly impossible: caller messages are single-line and may not begin with a trailer key (validate.rs:99-107; broker/state.ts:478-488), and `message_records_op` is line-exact (transport.rs:283-292).

What it does not preserve:

1. **The rebase path is silently lossy for non-whole-file semantics.** On `stale_state` from a *competing* writer, `commit_cas` re-issues the same whole-file upsert against the new head (transport.rs:248-250). If the competing commit touched the *same* file (the normal append case: two agents extending one events.log), the retry overwrites the competitor's bytes — the upsert is whole-file replacement, not a merge. The doc warns "only safe for whole-file upserts" (transport.rs:187-190) but nothing enforces it, and the one competing-writer test uses a *different* path, then asserts "the competing writer's file survives" (tests.rs:104-107) — the test is constructed to dodge the lossy case rather than expose it. For append-style mutations the doc defers to raw `commit()` + "reconcile explicitly," but no provided method reconciles explicitly, so callers are left to reinvent op-id checking.
2. **`already_applied: true` + `verified: false` is an incoherent compound outcome.** When the head carries our op id but different content (tests.rs:132-166), the resolution says "your write already applied" while simultaneously saying the content isn't yours. There is no distinct outcome variant; a caller that checks only `already_applied` concludes its write landed. The API invites exactly the misreading the content check was added to prevent.
3. **The read-back-mismatch (`502 upstream_error`) path has no reconciler.** The broker's contract says the write *may have landed* and callers must "reconcile before retrying" (broker/README.md; state.ts:415-424). `commit_cas` handles only `stale_state` (transport.rs:201-250). The reconciliation the broker demands — re-read head, check `Broker-Op:` trailer, verify content — is precisely what `commit_cas`'s `already_applied` branch does, but it is unreachable from the mismatch path. Gap between contract requirement and provided machinery.
4. Minor: the client's default retryability for `UpstreamError` is `true` (error.rs:112-116) while the broker's default for upstream errors is `false` (errors.ts:24, `options.retryable ?? false`). In practice every broker upstream error sets `retryable` explicitly (state.ts:93-118), so the divergence is masked — but the client's fallback is the *reverse* of the broker's fallback, which is the wrong direction to be wrong in.
5. Minor: `commit_cas` ignores `details.observed_head` from the stale error and re-reads state (extra round trip; harmless).

**Answer to Q6's core question: no — `commit_cas` preserves enough information to avoid lost updates *only* for whole-file-replacement semantics; for the append semantics v3 actually uses, the rebase path loses competing updates, and the read-back-mismatch case has no reconciliation at all.**

## 4. Per-agent-ref vs whole-tree-CAS analysis (Q4)

The v3 model's load-bearing semantics: per-agent refs with single-writer authority, fast-forward-only per-ref CAS, deterministic checkpoint composition (concurrent compactors produce identical bytes; hub_v3-excerpts.rs:44-52), REQ-11 prune as a controlled non-FF rewrite, and global total order by `OrderingKey` (events-excerpts.rs:12-24).

**A. Encode per-agent refs inside the broker tree** (`agents/<id>/events.log`, `checkpoint/state.json`, `meta/hub.json` as files under one tree):

- *Concurrency*: single-writer-per-ref becomes whole-tree serialization. Every append by any agent contends with every other agent's append; losers re-read and retry with growing `attempts`. v3's "agents never touch each other's refs" invariant is deleted, not adapted. Lock claim-confirm (first-claim-wins by `OrderingKey`) survives *correctly* (the global order is preserved), so correctness is recoverable — but the write model regresses from O(agents) parallelism to 1.
- *Limits*: a mature agent's `events.log` exceeds 256 KiB/file; the commit then fails client- and server-side validation with no remedy (no delete → no prune → no chunking without a new sub-convention). This is not an implementation nuisance; it means option A is only viable with chunk+index conventions and tombstones that are themselves a new state model.
- *Prune*: fast-forward-only CAS makes REQ-11's non-FF rewrite unrepresentable. Event logs grow monotonically forever. (Design doc's own assumption list concedes hub prune/rewrite paths are out of scope, §4 "Remaining assumptions".)
- *Idempotency*: replayed appends must dedupe by `OrderingKey` in the reducer — I could not verify from the excerpts whether `reduce` dedupes identical keys (unverified); if it does not, the lost-response replay case duplicates events.

**B. Extend broker later with finer-grained heads** (per-agent refs inside the project namespace, contract v2):

- *Semantics*: the only option that preserves v3's concurrency and prune model faithfully. It requires: `paths.ts` grammar extension, per-ref scope granularity (auth.ts — unverified), a v2 contract, redeployment, and migration of the single tree. The current trait shapes (`read_state` returning one head; `commit` with one `expected_head`) would become shims or be reworked.
- *Risk of deferral*: the trait is already public API in `lib.rs`; any production write path built against whole-tree CAS now calcifies option A. Reads (status, projection) are fine; writes are the calcification hazard.
- *Cost*: real, but bounded; and it can be staged (v2 adds `agents/<id>` sub-refs while keeping the tree for projections).

**C. Compose per-agent state into one project checkpoint** (v3 git refs remain the log of record; broker receives composed/derived state):

- *Semantics*: this is the only option implementable on v1 as deployed that preserves every v3 invariant. The broker tree holds deterministic, whole-file-replaceable material — exactly the property `CHECKPOINT_REF` already relies on ("two compactors over the same event set produce byte-identical content", hub_v3-excerpts.rs:44-52). CAS conflicts are benign; rebase-on-stale is safe because content is a pure function of the event set; no delete needed for checkpoints.
- *The catch*: this makes the broker a **cache/projection**, not the authority — which collides with the broker's stated purpose (credential-less workers mutating state, broker/README.md "Why"). A worker that cannot read per-agent refs (private repo, no credential) can see the checkpoint but cannot append events. If worker mutations must enter the event log, the broker tree needs a write-inbox region (e.g. `inbox/<worker>/<op>.json`) that a credentialed process drains into git — workable (op_id gives drain idempotency) but it is a *new* protocol with drain/replay/tombstone semantics that nobody has specified.
- *Consequence*: option C is coherent only as "broker = read projection + inbox," never as "broker = durable state of record." The design doc's step-4 plan (CAS one checkpoint file, §8.4) is implicitly option C but does not say so, and does not specify the inbox.

**D. Move/change the adapter boundary** (Crosslink-shaped ops — `append_events(agent_id, ...)`, `read_checkpoint()` — with git and broker backends):

- *Semantics*: strongest boundary; hides broker v1 entirely and makes the §4 mapping an implementation detail of the broker backend.
- *Cost*: it forces the mapping decision *now* and requires refactoring `SharedWriter`/`SyncManager` onto a trait, which the change's own constraint ("do not redesign Crosslink's hub v3 model", design §1) forbids. The deferral is therefore defensible — but see the calcification risk under B.

**Synthesis**: A is semantically corrosive (deletes two v3 invariants, dead-ends on limits). C preserves v3 fully but demotes the broker to cache+inbox, requiring an unspecified inbox protocol for worker writes. B is the faithful end-state but needs contract v2. D is right long-term but premature under the no-redesign constraint. The decision is genuinely unresolved, is *the* architecture of this integration, and everything currently in-tree (trait shape, projection conventions, the `tests.rs:287-290` hard-coded v3 layout inside a broker tree) silently biases toward A — the worst option.

## 5. Missing invariants (Q8)

1. **Projection freshness/provenance**: no persisted binding of projection contents to a broker head (see Q5.1). There should be one, with hydration refusing (fail-closed, like gh#125 r2) on mismatch.
2. **Backend-selection stability**: `StateBackend::resolve` is re-evaluated per call with no snapshot; env/file can change mid-run, and corrupt hook-config silently flips broker→local (Q5.2). There should be a "one backend per process invocation" rule and a hard error (not warn-and-Local) on corrupt config when a backend *was* selected.
3. **op_id uniqueness/ownership**: `commit_cas`'s reconciliation assumes single-writer-per-op-id (design §4 "Remaining assumptions") but nothing enforces it client- or broker-side; the failure mode is the compound `already_applied && !verified` outcome (Q6.2). The invariant should be stated as a caller obligation with a distinct outcome variant for violation.
4. **Whole-file-upsert-only precondition for `commit_cas`**: documented but unenforced (transport.rs:187-190). At minimum an invariant test that documents the lossy same-file rebase as forbidden/unreachable.
5. **Partial-mutation atomicity**: limits (32 files/1 MiB) guarantee some logical mutations cannot be one CAS commit; no invariant governs torn multi-commit sequences (no continuation marker, no "all-or-nothing at the logical layer" rule). Until the mapping decision, this should be an explicit non-goal with the consequence (no multi-file logical atomicity) written down.
6. **Baseline mismatch gates nothing**: `baseline.matches=false` is reported and printed (`commands/state_broker.rs:60-88`) but neither client nor (apparently) broker blocks commits on it (state.ts `commit` never consults the baseline — verified in state.ts:340-424). If baseline is meant to be advisory, say so; if binding, the enforcement is missing on both sides. (Interpretation; broker intent unverified.)
7. **Per-path write ownership**: v3 has single-writer-per-ref; the broker tree has no ownership rule at all. Required before any write wiring.

## 6. Missing tests (Q9)

Despite 3,000+ passing tests:

1. **`commit_cas` rebase onto a competing commit touching the same file** — the lossy case (Q6.1) is untested; the existing test deliberately writes a different path (tests.rs:79-107).
2. **Read-back-mismatch (`502 upstream_error` with `details.commit`) through the real HTTP client during `commit`**, and the absence of any reconciliation helper for it — the client-side test only checks the error is typed non-retryable (contract.rs:1149-1176), and `commit_cas` never sees it.
3. **The broker's 422→`stale_state` `unattached_commit` conversion** (state.ts:373-384) — the stub always updates the ref successfully; no client test exercises `details.unattached_commit`.
4. **Corrupt `hook-config.json` fallback to `Local`** (config.rs:437-443) — no test; this is the silent-backend-revert path.
5. **`StateBlob::bytes()` protocol error on digest/size mismatch** (client.rs:158-181) — no test serves a corrupted blob; the "broken transport must never surface as trusted state" claim is unproven end-to-end.
6. **Transport retryability classification** (`is_timeout`/`is_connect` → `retryable`, client.rs:523-528) — untested.
7. **`state-broker status` CLI behavior** — only a `host_label` unit test (commands/state_broker.rs:148-159); the design doc's CLI smoke results are manual, not automated.
8. **`hydrate_into` with an explicit subset at a pinned head** — subsets are validated (tests.rs:36-46) but the "reads at head, not at request time" pinning property (all blobs at one commit) is asserted nowhere; a torn multi-blob projection (head moves mid-hydration) is the exact failure the v3 sources guard against with pinned SHAs (hub_source.rs:31-38) and the adapter's `hydrate_into` has no equivalent pinning test or guarantee beyond reading `Some(&head.commit)` per blob (transport.rs:170) — between blobs the head can move, and nothing detects it.
9. **max_retries > 1 with real (non-injected) repeated conflicts** — only exhaustion via injected failures (tests.rs:168-188).

## 7. Coupling inventory (Q7)

- **Git**: 40-hex lowercase sha grammar hard-wired in validation (`is_commit_sha`, validate.rs:152-159), `expected_head`, `verify(commit, …)`; ref grammar `refs/heads/projects/<uuid>/state` baked into `StateBrokerConfig::state_ref/state_branch` (config.rs:292-303); `pseudo_git_sha` git-shaped identifiers for fixtures (digest.rs:14-19). Coupling to git is intrinsic to broker v1 (it *is* a git facade) and acceptable — but `CommitOutcome`/`CasResolution` leak raw commit shas to future Crosslink call sites, so if broker v2 ever changes the backend abstraction, the leak is already in Crosslink's hands.
- **Broker v1**: deepest coupling sits *inside the seam*: `commit_cas`'s trailer parsing (`Broker-Op:`, transport.rs:283-292); the 8 wire codes with a "MUST NOT be renamed" contract note (error.rs:34-37); limits duplicated in validate.rs with an explicit "MUST stay in sync" comment (validate.rs:1-5); and a third copy in the stub. Substituting the broker means rewriting the trait's provided methods, not just an impl.
- **Crosslink v3 layout**: the projection test hard-codes `checkpoint/state.json` and `meta/hub.json` inside a *broker* tree (tests.rs:287-290), and `read_checkpoint` consumes the v3 file layout — nudging the broker namespace toward embedding v3 layout (option A) before the mapping decision. Additionally, `projection_relative_path` rejects Windows-reserved segments (validate.rs:205-214) that the *broker* accepts (paths.ts has no such rule): a legal broker state file (`aux/x.json`) is un-hydratable by the client — the durable truth and the projectable projection can diverge, and the client treats the broker path grammar as stricter than it is.
- Also: two ref grammars will coexist (`refs/heads/crosslink/*` vs `refs/heads/projects/<uuid>/state`) with nothing relating them — the mapping decision must own this.

## 8. Recommended next step (Q10, Q11)

**Q10**: `SyncManager` wiring must **not** follow the live smoke test directly. The live test validates only the read contract (it performs zero writes, tests/state_broker_live.rs:1-14); it de-risks none of the write-side semantics — concurrency model, prune, limits — where all the unresolved risk lives. The design doc's own §8.4 and the handoff resume note (handoffs/issue-802…: "do not wire `SyncManager` to the broker before that decision") already say this; I independently confirm it. A design/invariant decision is required first.

**Q11 — smallest next architectural step**: produce a one-decision design note that takes the §4 fork explicitly, forced by a concrete write-path walkthrough: specify, end-to-end on broker v1, how *one* v3 mutation (an agent appending one event) becomes a broker commit — including conflict behavior, replay/idempotency, the 256 KiB/1 MiB limits on a mature log, REQ-11 prune, and where worker-originated mutations enter. The walkthrough's predictable failure (append + no-delete + whole-tree CAS cannot satisfy prune or bounded logs) is the decision procedure: it rules out A, and forces the choice between **C** (broker = read projection + inbox; v3 git remains the log of record — implementable on v1 today) and **B** (contract v2 with per-agent heads — the faithful end-state). My recommendation, on the semantics: C now, B as the tracked v2 goal. Accompany it with the two cheap invariant fixes from §5 (projection provenance marker; hard error on corrupt hook-config when a backend was selected) — both are small, and both close paths by which the wrong store silently becomes authoritative.

## 9. Confidence and main uncertainty

**Confident** (read directly, cited): the trait/broker-shape analysis (§1); the lossy same-file rebase in `commit_cas` (§3, Q6.1); the compound `already_applied/verified` outcome; the missing read-back-mismatch reconciler; the corrupt-hook-config silent fallback; the absence of projection freshness markers; the limits-based dead-end of option A; that nothing currently wires the broker into the write path; that the Hy3 major finding is genuinely fixed and its minor findings were addressed (stub fidelity, `pub(crate)` expose at config.rs:100, exact control-char rule at validate.rs:85-90).

**Could not verify**: whether the v3 reducer dedupes events with identical `OrderingKey` (bears on option A's replay safety); `broker/auth.ts`, `config.ts`, `github.ts`, and the broker tests (scope/limit enforcement details inferred from app.ts/state.ts only); the actual `git update-ref`-equivalent ref-update semantics behind `gh.updateRef` (the 422 analysis is from state.ts's handler, not the GitHub API behavior); any claim about `crate::utils::is_windows_reserved_name` internals; test counts and flake claims are taken from the handoffs, not run.

**What would change my mind**: (1) evidence that the reducer dedupes by `OrderingKey` and that a chunking/tombstone convention is already specified somewhere outside this packet — that would rehabilitate option A; (2) evidence that the broker is *intended* only as a Codex Cloud convenience (never Crosslink's durability path) — that would make C the whole story and dissolve most of the §4 tension, at the cost of making the `SyncManager` question moot; (3) a broker v2 roadmap already committed elsewhere — that would move B from "extend later" to "wait."
