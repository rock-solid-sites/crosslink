## Blocking findings

- **B1 — Broker-only reconstruction can reach the hydration seam with no provenance enforcement.**
  Evidence: `CDP-1-spec.md:619-631` (§6.1: only the journal-anchored profile may treat a read as derived from durable journal state; broker-only reads "must never be used for exclusivity, prune, or display-id"); `CDP-1-spec.md:668-672` and `:908` (the git/`state_blob_sha` cross-check is "optional"); `CDP-1-spec.md:917-920` ("`checkpoint/state.json` … is fed to the existing `read_checkpoint`/`hydrate_from_state` path"); `transport-design.md:96-104`; contrast `ADR-802.md:82-84` ("No Crosslink decision may depend solely on broker state") and `ADR-802.md:179-181`.
  Why it blocks: The reader (§6.2 / Appendix B `CDP-1-spec.md:1206-1234`) returns an `VerifiedCheckpoint{commit, manifest, state, state_bytes}` that is **identical** for both profiles, and the projection freshness gate (§9.3) passes steps 1–6 without any git access (step 7 is parenthetical/optional). So a broker-only, self-consistent-but-forged or merely unprovenanced reconstruction can be hydrated into SQLite and drive display-id/lock decisions — the exact ADR-802 §3/§8 prohibition. The "advisory only" rule is stated as convention, not encoded in the reader/projection types or the hydration seam. The design, as the implementation contract, must add a provenance bit (e.g. `VerifiedCheckpoint.provenance ∈ {JournalAnchored, Advisory}`) that `hydrate_from_state`/any decision-making consumer is required to check. Open question 8 (`CDP-1-spec.md:1037-1041`) raises this but does not resolve it; the spec's own pseudocode permits the unsafe path.

- **B2 — The capacity model's Wire-accounting fallback is arithmetically wrong, and the evidence the spec cites to resolve decoded-vs-wire does not exist.**
  Evidence: `CDP-1-spec.md:827-837` (§8.5: "If the deployed broker actually counts the base64-encoded wire body, the commit budget becomes 786,432 decoded bytes and the payload capacity 782,336 bytes (3 slots)"; "the loopback boundary test (§10 H6) … are the evidence that resolves it"); `CDP-1-spec.md:751-807` (§8.2–8.3 present the current hub as "43.8 % of capacity, 2 of 4 slots"); `validate.rs:14-17` and `:383-394` (client mirror checks **decoded** `file.content.len()` against `MAX_FILE_BYTES`/`MAX_TOTAL_BYTES`); `tests-state_broker_contract.rs:837-843` (the loopback stub also counts **decoded** bytes); `live-smoke.md:77-79` ("the size rule is untested live"); `CDP-1-spec.md:1006-1007` (open Q1).
  Why it blocks: (a) Under Wire accounting the per-file cap also shrinks: a full slot of `SLOT_BYTES = 262,144` decoded bytes encodes to `ceil(262144/3)*4 = 349,528` base64 bytes, which exceeds a 262,144 wire per-file cap. §8.5 rescales only the *commit* budget (to 786,432) and keeps `SLOT_BYTES = 262,144` across "3 slots," so its own Wire configuration violates the per-file limit; and the **current** 457 KiB hub (chunks 262,144 + 195,102 decoded → 349,528 + 260,136 base64) is **unpublishable** under Wire, contradicting §8.3's "comfortably fits" framing. The Wire model must also halve `SLOT_BYTES` (to ~196,608 decoded) and recompute. (b) The spec asserts the loopback boundary test resolves the question, but the stub mirrors the client's decoded assumption (`tests-state_broker_contract.rs:837-843`), so a loopback test can only confirm the stub's model, never falsify it — only the live probe on a synthetic project can. (c) The cited "§10 H6" test does not exist: §10 enumerates T01–T39 (`CDP-1-spec.md:924-971`) with no H6, and T21 is level **U** (unit math), not a loopback test, yet §12 item 12 (`:1094`) lists "T21, T35, H6" as the resolution. Because the feasibility of publishing the actual hub depends entirely on this unresolved question and the spec's stated evidence path is invalid, the capacity analysis cannot be certified as written. (Mitigating: the runtime failure mode is a clean `invalid_input` reject via the broker being authoritative — `validate.rs:6-8` — not silent corruption; but the design's central capacity claim and its resolution test are both incorrect.)

## Non-blocking findings

- **N1 — Reconciliation "verify(X, owned_paths)" over-verifies the full 4-slot namespace.**
  Evidence: `CDP-1-spec.md:540` and `:1188-1190` ("if verify(carried_commit, owned_paths) all match → LANDED_SUPERSEDED"); `owned_paths` is defined as `{manifest} ∪ {chunks/0000..0003}` (`CDP-1-spec.md:453-454`); contrast `transport.rs:677` / `:420` which verify `request.paths()` (the active `1+chunk_count` written paths). Why it matters: for a publish that wrote `n<4` chunks, verifying all four slots at a superseded commit X reports `present:false` (or stale content) for the unlisted slots, so "all match" fails and a genuinely landed-and-superseded publish is mislabeled `NotLanded`. It self-corrects on the bounded retry (re-classifies to `AlreadyCurrent`), so no data is lost, but the outcome label is wrong and can mask a landed publish. The spec should say "the active paths in this request," matching `transport.rs`.

- **N2 — `AlreadyCurrent`/`Diverged` keyed on `source.commit` equality yields a false terminal Diverged on content-identical checkpoint re-commits.**
  Evidence: `CDP-1-spec.md:476-477` (`head.W == W` requires `source.commit == S` **and** `state_sha256 ==` for `AlreadyCurrent`; otherwise "semantic identity differs" ⇒ `Diverged`, "hard block"); `hub_v3-excerpts.rs:182-199` (compact_v3 skips re-commit only when `state.json` is byte-identical **and** the browse tree is present); `CDP-1-spec.md:567` ("`Diverged` is terminal without operator intervention"). Why it matters: when the checkpoint ref is re-committed with byte-identical `state.json` but a different commit sha (e.g. bootstrap/migration `state.json`-only commit `S1`, then the first `compact_v3` that adds the browse tree producing `S2` with the same `state.json` and same watermark), a publish of `S2` against a broker head carrying `S1` hits `head.W==W`, `commit != S` ⇒ `Diverged` even though the content is identical. This can permanently wedge the derived publish (terminal, operator-only) on a legitimate transition. Content identity (`state_sha256`, which subsumes `W`) should drive `AlreadyCurrent`; commit-sha equality should not force Divergence when `state_sha256` matches.

- **N3 — §7.7 slot-namespace bound contradicts `MAX_SLOTS`.**
  Evidence: `CDP-1-spec.md:741-743` ("Slots are fixed at `0000..0031` (practically `0000..0003`)"). Why it matters: with `MAX_SLOTS = 4` (`:235`, `:761`) the namespace is `0000..0003`; `0031` conflates the 32-file commit cap with the slot count. Harmless to the algorithm but the "bounded namespace" proof should state the correct bound.

- **N4 — Definitive refusals collapse into `ReconcileRequired`, losing the ambiguity/refusal distinction.**
  Evidence: `CDP-1-spec.md:1148` (Appendix A maps every `Refuse(reason)` to `return ReconcileRequired(reason)`); `CDP-1-spec.md:518` defines `ReconcileRequired` as "unknown or unprovable"; `CDP-1-spec.md:472-478` lists definitive refusals (`OverlapUnprovable`, `HeadManifestUnreadable`, `WrongProject`, `CandidateStale`). Why it matters: `CandidateStale` and `WrongProject` are certain, not ambiguous, yet are reported as "resolve by re-read; operator if persistent." The taxonomy (`:510-520`) has no `Refused` outcome, so a caller cannot distinguish "your input is wrong, stop" from "outcome unknown, reconcile." No write occurs either way (safe), but the outcome contract is imprecise.

- **N5 — Historical-commit reads are load-bearing but verified only against mock/stub, not live.**
  Evidence: reader pins every blob to `Some(C)` (`CDP-1-spec.md:641`, `:652`) and reconcile does `verify(X, …)` at a superseded commit `X != head` (`:540`, `:1188`); `mock.rs:306`/`:344` and `tests-state_broker_contract.rs:408`/`:445` serve arbitrary commits from a `history` map; but `live-smoke.md:63` read blobs "at pinned head" only, and `ADR-802.md:368` records "no live broker call." Why it matters: the deployed broker's retention/serving of arbitrary non-head commits is an unverified assumption underpinning both pinning and superseded-commit reconciliation. It is consistent with the v1 client surface (`client.rs:567`, `:587`) but should be listed as an explicit §12 gate/assumption.

- **N6 — Evidence-packet revision mismatch weakens the "current code enforces X" claims.**
  Evidence: `tests-state_broker_contract.rs:1062-1088` uses a struct-shaped `CasResolution` (`resolution.already_applied`, `resolution.outcome`) and `error.is_readback_mismatch()` (`:1158`) and `blob.text()` (`:932`); the hardened `transport.rs:156-188` defines `CasResolution` as an **enum** (`Applied`/`AlreadyApplied`/`ReconcileRequired`) and `error.rs` has no `is_readback_mismatch`. Why it matters: the loopback contract test is from a pre-hardening revision, so §10.1's "the hardening branch already made the stub history-aware" (`CDP-1-spec.md:996-997`) and the §12 gate statuses cannot be tied to a single coherent revision as the hardened `transport.rs`/`error.rs`/`projection.rs` provided. The hardened `state_broker/tests.rs:366-371` *does* use the enum shape, confirming two revisions are mixed in the packet. This is an evidence-consistency caveat, not a spec defect, but it means the claim "the loopback boundary test resolves accounting" (§8.5) cannot be validated against the same code the spec's §12 gates reference.

## Incorrect or unsupported assumptions

- **"The loopback boundary test resolves decoded-vs-wire accounting."** Unsupported: the stub mirrors the client's decoded check (`tests-state_broker_contract.rs:837-843`; `validate.rs:389-394`), so it cannot falsify the decoded assumption; only a live probe can. Also the cited "§10 H6" does not exist (§10 = T01–T39, `CDP-1-spec.md:924-971`), and T21 is level U, not loopback. (See B2.)
- **"The current hub is comfortably within capacity (43.8 %, 2 of 4 slots)."** Only true under the *decoded* assumption; under Wire it is false at the per-file limit (a 262,144-decoded slot → 349,528 base64 > 262,144). §8.3 presents it without that contingency. (See B2.)
- **"Broker commits always carry the caller's `Broker-Op:` trailer, and the broker exposes no ancestry API."** The trailer format is confirmed live (`live-smoke.md:44-52`), but "every successful commit carries it" and "trailer + atomicity is the attribution mechanism" (`CDP-1-spec.md:558-560`) is asserted, never exercised live (`live-smoke.md:118-119`: reconcile/trailer path "not exercised live"). Material to §5.7's `NOT_LANDED`-is-safe argument.
- **"gzip is mandatory because the hub exceeds both caps uncompressed."** Supported: raw 1,846,959 > 1 MiB and gzip-9 457,246 > 256 KiB (`checkpoint-size-evidence.md:7-9`). But ADR §1 quotes gzip ≈ 459,884 while the spec/size-evidence give CLI 459,858 / zlib 457,246 (`ADR-802.md:41` vs `CDP-1-spec.md:797`) — a trivial unreconciled figure, not load-bearing.
- **Byte-determinism of `flate2`/`miniz_oxide` across runtimes.** Not verifiable from the packet (no dependency/build present); correctly flagged as open Q2 (`CDP-1-spec.md:1008-1012`). The protocol's safety does *not* depend on it (semantic-identity comparison, `:216-221`), so this is an optimization assumption, not a correctness one — but §2.4's "byte-identical replay ⇒ no-op" rationale is misattributed: the no-op comes from `AlreadyCurrent` on `W`+`state_sha256`, not byte identity (see N2).
- **Repository↔project-UUID binding.** The manifest's `project_uuid`/`state_ref` are validated only against *config/token* (`CDP-1-spec.md:388-389`; `client.rs:543-556`); nothing binds the git repo that produced `S` to the UUID, and the manifest carries no source-repository field (`§4.4/§4.5`, `:404-429`). A wrong-repo publish is undetectable from the manifest. Open Q3 (`:1013-1018`) and §12 item 9 (`:1083-1085`) acknowledge this but do not resolve it.

## Missing invariants / missing tests

- **Provenance-enforcement invariant (B1):** no invariant prevents an `Advisory`/broker-only `VerifiedCheckpoint` (or a freshness-passing projection without step 7) from reaching `hydrate_from_state`. Missing test: a hydration call fed a broker-only reconstruction must be refused; T36 (`:968`) only checks the reader "cannot claim provenance," not that hydration *rejects* the non-provenanced artifact.
- **Per-file Wire boundary (B2):** no test pins the slot size to the actual accounting; T21/T35 test decoded boundaries only. Missing: a live/proven synthetic probe that a full 262,144-decoded slot is accepted by the *deployed* broker.
- **Content-identical re-commit (N2):** no test for `head.W==W`, same `state_sha256`, different `source.commit` → must be `AlreadyCurrent`, not `Diverged`.
- **Superseded-commit verify over the active set (N1):** T18 (`:950`) covers "head moved past our commit," but no test asserts reconcile verifies only the `1+chunk_count` written paths (not all 4 slots) at a superseded commit.
- **Historical-commit serving (N5):** no test that the deployed broker serves arbitrary non-head commits; mock/stub only.
- **Manifest-size vs unbounded `compression_impl`:** §4.1 leaves `compression_impl`/version strings unbounded; only M12's 4,096 fail-closed (`:398`) saves it, and no test drives a long `compression_impl` to the cap.
- **Concurrent same-`S` publishers:** T12/T13 test same-watermark replay/divergence against a static head; no test races two publishers of the same `S` landing interleaved through the §5.8 state machine.

## Readiness

**ready after named corrections.** The protocol is unusually rigorous on the safety-critical spine — watermark monotonicity, the digest ladder, single-commit atomicity, no-delete fixed-slot inertness, the landed/not-landed/unknown trichotomy, semantic-identity CAS, and the correct prohibition on reusing generic `commit_cas` (`CDP-1-spec.md:1078-1082` vs `transport.rs:586-785`) all hold up against the evidence. Before it becomes an implementation issue it must: (1) encode a provenance bit on the reader/projection/hydration seam so broker-only state cannot drive SQLite or decisions (B1); (2) correct the Wire-accounting model to shrink `SLOT_BYTES` as well as the commit budget, restate §8.3's feasibility as decoded-contingent, and point the decoded-vs-wire resolution at a live boundary probe rather than the nonexistent "H6"/loopback test (B2); and (3) close the smaller items N1–N6. None of these require redesign; they are spec corrections plus two added invariants/tests.
